# 接管材料化 v1

业务盘点只证明旧数据库可以完整读取，不代表旧服务目录可以直接作为 gitsss 数据目录。`takeover.materialize` 因此在隔离恢复之后生成一个全新的数据代：内置 `gitsss.db`、扁平且稳定 ID 的仓库目录、LFS 根、附件/软件包/流水线留档、源数据库快照和材料化清单。原隔离副本保持只读，输出目录必须尚不存在，失败输出会整体清理。

SQLite、PostgreSQL 和 MySQL 快照中的用户、组织、仓库、Issue、PR、评论、发布、标签、里程碑、附件、团队及关系表按确定性顺序写入 `source-import-*` 命名空间；超过单条状态文档上限的记录写入受保护的 oversize 区，并在数据库中保存相对路径与 SHA-256。完整源数据库快照仍保留在 `imports/source-database`，所以未识别表不会静默丢失。仓库从 `data/repositories` 复制到 gitsss 托管根并写入 `repository-catalog`；旧 wiki 仓库只留档，不会注册成普通仓库或执行旧 hooks。

材料化前会保守估算“恢复副本全部文件 + 一份数据库快照”的写入量，并使用输出卷实时容量保留 10 GiB 安全空间。目录树拒绝符号链接、特殊文件、超过一千万项的输入以及数据库仓库数与 bare 仓库数不一致的情况。

`gitsss-materialization.json` 绑定源数据库 SHA-256、业务清单 SHA-256、最终活跃路径、导入计数和内容树 SHA-256。最终 `takeover.cutover` 会重新运行源/恢复影子审计，再重新计算材料化内容摘要；只有两个摘要、目标活跃路径和人工确认同时匹配，才会把材料化数据代原子切入。原始恢复副本不能再直接切换。
