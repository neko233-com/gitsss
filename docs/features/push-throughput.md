# 同仓库、同分支 push 吞吐与兼容性

验收目标为同一个仓库的 `refs/heads/main` 每秒至少 100 次成功更新。一次 push 必须是独立的 Git receive-pack 事务，包含真实的新提交并成功更新该分支；拒绝、重试、无变化请求和一次 push 中的提交数量均不计入成功次数。

同一分支仍执行 Git 的旧 OID 比较和原子 refs 更新。两个基于同一个旧 HEAD 的不同提交不能同时覆盖彼此；旧值不匹配、非快进和受保护分支拒绝必须单独验收。并发上传、解包和权限校验可以重叠，最终分支更新仍有确定顺序。

## 兼容性与存储影响

本轮首先提供隔离、可复现的 smart-HTTP 基准，定位认证、receive-pack、hooks 和数据库处理开销。任何优化必须继续使用现有仓库目录、Git 对象、refs、LFS 对象和数据库 schema；不引入替代 WAL、对象服务或新的持久化格式。

- 迁移：现有仓库、LFS 对象、账号、权限和路径不需要迁移；基准只创建独立的 Docker 数据卷与测试账号。
- 回滚：回退服务端二进制即可；不得为性能结果改写对象、refs 或 layout v1。
- 容量：测试报告记录上传字节、提交数量、Docker 数据卷类型和服务端二进制身份。测试数据使用 Docker 持久卷，不使用内存文件系统充当仓库存储。
- 性能：普通 Git CLI 与预构造的标准 smart-HTTP 请求分别记录；协议驱动的结果不能当作 Windows CLI 端到端耗时。报告成功吞吐、p50/p95/p99、拒绝次数和重试次数，不只展示请求发送速率。
- 权限与持久化：不得跳过 hooks、权限、保护分支、旧 OID 比较或既有 fsync 策略。重启服务后再次读取最终分支，并校验对象完整性。

## 本地验收

`tools/benchmark-push.py` 使用本地构建的服务端、隔离 HOME/USERPROFILE/SSH_ROOT_PATH、独立 SQLite 和 Docker 数据卷。禁用测试实例的 Actions 与系统 SSH 授权文件写入。测试生成的凭据只用于该实例，不写入报告或命令日志；结束时仅删除该次创建且标签匹配的容器和数据卷。

顺序负载每次提交修改一个小文本文件；并发负载使用同一分支的已知线性提交链，保持每个事务的 expected-old OID，单独统计竞争拒绝与重试。另以相同旧 HEAD 的两个不同新提交验证恰好一个成功，不能将分支冲突隐藏为成功。

默认并发调度为连续固定在途数（`--concurrent-scheduling continuous`），完成一个请求后补入下一个。每次 pack 最多携带 worker 数量的滑动祖先窗口，避免尚在途的父对象造成连接性拒绝；每次请求仍只更新一个 refs/heads/main 到一个新的唯一提交。`windowed` 保留逐组等待全部请求结束的对照方式。报告同时记录调度方式、上传字节和成功事务数量。协议吞吐阶段独立运行，随后将 Windows CLI 与另一个隔离仓库的 Git/LFS/PR 功能验证并行执行。

v1.16.0 最终 Linux amd64 CGO 包在 WAL/NORMAL 配置下通过：16 个连续在途请求、512 次独立成功更新、零重试，119.76 push/s；含本机 Git/LFS/PR、权限、自定义 hooks、真实数据库记录、重启与对象完整性的整批验收耗时 50.907 秒。完整数据见 [验收报告](../benchmarks/same-branch-push-20261021.json)。Cursor 的公开架构可作为设计参考，其 S3 WAL 与条件写入方案不能直接替换本项目冻结的存储契约。

## 轻量 hook 接收链路兼容性报告

2026-10-21 的 Trace2 定位中，普通 Git 子进程平均约 1.4 ms，而前置、update、后置 hook 平均约 52 / 42 / 60 ms。update 内置业务几乎为空，主要成本来自完整 GitSSS 应用的包初始化。这是诊断样本，不能作为优化后的吞吐结果。

实现采用随服务端构建的 `gitsss-hook` 轻量客户端和每次 receive-pack 的临时 `core.hooksPath` 覆盖。只有顶层分发器与 `*.d/gitea` 内置委托均匹配当前受信模板、没有自定义 hooksPath 且本机内部 HTTP 可用时才启用；否则保留原链路。轻量客户端继续使用现有内部 API 执行权限、保护分支、提交与分支数据库处理，不缓存授权决定。自定义 hook 的顺序、输入、参数和退出结果保留；额外内部认证环境不传给自定义脚本。

- 迁移：不修改既有 bare 仓库或其 hooks，不改对象、refs、LFS 字节、数据库 schema、认证协议或用户配置。代理脚本只放在 layout v1 允许的 `gitsss/extensions/receive-hooks/`，逐次命令覆盖不写入仓库配置。
- 回滚：回退原服务端二进制即可；原 hooks 和配置始终保留。删除辅助程序会恢复原链路；扩展目录可保留供诊断。
- 容量：增加一个与服务端同架构的小型辅助程序和共享代理脚本，不复制仓库或对象，不引入 WAL。实际大小由最终包记录。
- 性能与可靠性：不降低 fsync，不合并多次 push 来增加计数，不跳过前后置处理，不增加全仓库互斥锁。Git 原生事务仍负责旧 OID 比较和原子更新。需要完整验证自定义 hook、保护分支、失效授权、并发竞争、重启持久性和真实同分支成功吞吐。

同分支流水线仅登记当前 HTTP 请求中的 refs/OID 依赖。在权限和前置校验完成后，若其 expected-old 正是另一个在途事务的新 OID，最多等待 250 ms；Git 的 post-receive 告知 refs 已提交后唤醒。失败、取消和结束也释放登记，之后仍由 Git 原子比较旧 OID，过期旧值不会被自动替换。登记只在内存中，不是 WAL 或数据存储；没有全仓库互斥，其他 refs 不等待。未知、签名扩展或过大头部保持原始字节交给 Git，不做依赖调度。

该链路已通过最终包的本地批量验收，达标配置为 Linux CGO、WAL、NORMAL；其他同步级别和客户端路径分别记录。Git hook 契约见 [官方文档](https://git-scm.com/docs/githooks)，Cursor 的对照架构见 [Git at any scale](https://cursor.com/blog/git-at-any-scale)。

## 并发元数据与认证热路径

SQLite 同步级别的兼容性范围：新增 `[database] SQLITE_SYNCHRONOUS`，留空保留原驱动默认（CGO NORMAL、纯 Go FULL），显式支持 `FULL/NORMAL/EXTRA/OFF` 并应用于每条数据库连接。现有缓存策略与默认值保持不变。此项不改变 schema、数据库路径、日志模式、Git/LFS 字节或存储布局，无需数据迁移；回退旧二进制可直接读取原数据库，新键可保留但旧版本不使用它。同步选择不增加新的持久文件，WAL 的 db-wal/db-shm 容量与备份要求仍遵循已有配置。吞吐报告须标明实际驱动、日志模式和同步级别，NORMAL 与 FULL 分开记录。推荐的接收能力验收配置为 Linux Docker/CGO、WAL、原驱动 NORMAL，不修改 Git 原有 fsync 策略。

同一分支的 post-receive 回调可能乱序到达。分支元数据回写先核对当前 Git ref，再以读取到的数据库 commit_id 作条件更新；过期回调不覆盖新快照，竞争失败后重新读取。单 ref 使用条件写入，不在读取 Git 对象期间持有 SQLite 读事务；多 ref 与原有批量事务兼容。每次 push 的后续活动与通知仍走原队列，不因快照已过期而丢弃事件。

修复数据库模型初始化回调的注册条件，使原有令牌 ID 缓存按 `SUCCESSFUL_TOKENS_CACHE_SIZE` 正常初始化。缓存命中后仍逐次查询数据库，保留令牌撤销与 scope 变更检查。认证只更新最近使用时间，不用过期令牌快照重写名称、scope、哈希或盐；同一秒内重复认证无需再次写入活动时间。令牌格式、权限、数据库 schema 和配置键不变。

## 验收进度与运行方式

2026-10-21 本地持久 Docker 卷的已记录结果：完整应用 hook 的基线顺序约 5.47 push/s；轻量 hook 与修复前的在途协调顺序约 14.05、并发约 9.94 push/s，并暴露数据库回写乱序。加入快照条件更新后的 128 + 128 次批次数据库记录匹配通过。令牌热路径修复后的容器内回环结果为顺序 18.84、并发 22.34 push/s，仍未达到 100 push/s，不能作为生产吞吐达标结论。

`--load-location windows-host` 记录 Windows 到 Docker 的协议路径；`container-loopback` 使用同一负载函数在容器内测量 HTTP 接收能力。Windows 原生 Git CLI 仍单独记录。`--sqlite-journal-mode default` 保持实例原有默认；显式 `WAL` 或 `DELETE` 只用于独立测试实例的配置对照，不修改工作站或生产配置，不降低 synchronous/fsync 策略。`--diagnostics-dir` 仅保存本地 Trace2、CPU 与等待时间分析，不发布原始诊断文件。

辅助程序必须与服务端来自同一版本，并作为同目录的 `gitsss-hook`（Windows 为 `gitsss-hook.exe`）安装。Docker 镜像与 `make backend` 自动包含它；`build/release-native.sh` 为各平台同时生成主程序和带版本的辅助程序，手动安装时将辅助程序恢复为上述固定文件名。缺失、不兼容或自定义 hook 模板时回到原有链路。发布必须同时校验这两个产物及 SHA256SUMS。

原生发布的 XZ 压缩优先使用 `xz`，缺失时使用 Python 3 标准库 `lzma`，可用 `PYTHON` 指定解释器。回读全部 XZ 并比对原始文件 SHA-256 后才能发布；压缩回退不改变主程序、辅助程序或校验文件的内容契约。

Unix 的内置 hook 通过指向辅助程序的共享链接直接执行；Windows 继续使用 shell 代理。只有分发器和唯一内置委托都匹配受信模板才跳过 shell，发现自定义脚本时执行原分发器。自定义子进程清除内部认证环境，并恢复原 hooksPath，保留其他继承的 Git 配置，使嵌套 Git 命令继续执行原 hooks。链接仅位于扩展目录，不覆盖 bare 仓库的 hooks。

8/16/32 并发的 CGO + WAL 初步样本为 102.56 / 125.47 / 122.94 push/s、各 128 次成功且零重试，使用原驱动 NORMAL 默认。FULL 对照批次的最高值为 72.20 push/s；该对照的功能、真实数据库记录与重启完整性通过，吞吐未达 100。最终构建已通过 512 次提交统一批次：连续 16 并发 119.76 push/s、零重试；完整功能批次 50.907 秒。
