架构设计

上游基线、产品边界、兼容性规则

产品定位

gitsss 是面向公司内网的自维护 Git 协作平台。代码基线复制自 Gitea v1.27.1，运行时不依赖 Gitea 应用库。唯一公开命令为 gitsss。

核心原则

一个服务器、一个 UI 布局、一个产品数据模型。不存在第二个生产入口或界面。

服务启动时按配置自动创建全局 gitsss-builtin Runner，使用现有 Actions API 回环轮询；外部 Runner 仍可并行使用。新增配置只影响 Runner 启动，不改变数据库、Git、LFS、工作流目录或 API 合同。

导入边界

以下内容不从上游导入：

  • .git、.github、.gitea
  • 上游 Agent 指令
  • 上游产品 README
  • 上游 CI Workflow（不跟踪、不启用）

之前的独立 server/ 和 React web/ 实现在集成以下三个概念后被移除：

  1. Git 存储基础 — 底层存储引擎
  2. 存储感知 — 容量监控和写入保护
  3. 运维数据大盘 — 运行状态可视化

这些行为现在以平台原生的 models、services、routers、templates 和前端资产实现。

兼容性规则

以下内容必须保持 Gitea 兼容语义，直到接管验证通过：

  • 数据库 ID
  • 密码哈希
  • 两因素认证密钥
  • SSH 密钥
  • Access Token
  • 仓库路径
  • LFS 对象
  • Actions 数据
  • app.ini 配置
Schema 规则

Schema 变更必须是增量且可逆的，在迁移窗口期内不能破坏兼容性。

Git 核心数据

服务端使用 Go 1.27.2 构建。升级可以更换二进制，但不能搬迁或重写裸仓库、Git 对象、refs 和 LFS 对象字节。布局合同版本 1 记在数据目录的 gitsss/layout.json。后续功能只能把扩展文件放到 gitsss/extensions/<id>/，并在清单的 reserved 里登记。更旧的程序如果读到更高的 layout_version，必须停止且不写这些目录。回滚就是换回上一版程序，Git 与 LFS 数据不需要迁移。

离线规则

运行时启动、仓库使用、迁移和支持的 Actions 工作流不得需要公网访问。构建输入和捆绑 Action 通过 digest 验证镜像到单个发布镜像中。

GitLab 仓库约定

gitsss 在迁移和正常使用中接受常见的 GitLab 仓库约定：

文件用途
.gitlab/CODEOWNERS自动 PR 审查人选择和保护分支审批
.gitlab/merge_request_templates/Default.md默认 PR 描述模板
.gitlab/MERGE_REQUEST_TEMPLATE.md单个 MR 模板
.gitlab/issue_templates/*.mdIssue 模板选择器
.gitlab/ISSUE_TEMPLATE.md默认新建 Issue 描述

已有的 CODEOWNERS、docs/CODEOWNERS、.gitea/、.github/ 约定继续有效。按文档中的候选顺序使用第一个匹配文件。
