开发指南

本地开发、代码规范、测试与发布

前置条件

  • Task — 任务运行器
  • Docker — 构建容器镜像；日常编译和测试可以不启动它
  • Go 1.27.2 — 后端开发与发布工具链
  • Node.js LTS + pnpm — 前端开发

前端依赖使用 pnpm-workspace.yaml 管理 overrides 与构建脚本许可，默认使用冻结锁文件安装；Scarf 安装分析已关闭，适合内网和离线构建。

Docker 可用时，task fmt、task test:go 仍走容器，保证环境一致。没有 Docker，或设置 GITSSS_TASK_NATIVE=1 时，这些命令直接在本机执行。只要后端二进制时用 make backend-quick，它不会再全仓库跑 go generate。

快速开始

# 查看所有可用命令
task help

# 本地构建并运行
task build
task start

常用命令

命令用途
task help查看所有可用 Task 目标
task fmt格式化 Go 和前端代码
task lint:goGo 静态检查（golangci-lint）
task lint:jsJS/TS 静状检查（eslint）
task test运行全部测试
task vbox:verify使用 github.com/neko233-com/vbox 替代 Docker 做本机 GitSSS HTTP 验证
task build构建前后端。Docker 可用时在容器里执行
make backend-quick只编译后端，跳过全仓库 go generate
task build:host本机编译前后端，不启动 Docker
make release-native VERSION=1.2.0本机并行交叉编译，默认 2 个任务、xz -6；要求工作树干净且前端资产戳匹配，自动生成源码包、平台 tar.gz、逐文件校验和与 SHA256SUMS 回读。用 DIST=dist/1.2.0 隔离输出，RELEASE_GOGIT=1 额外打 Windows Go-Git 包，XZ_LEVEL=9 使用更小但更慢的压缩
task release VERSION=1.2.0 DIST=dist/1.2.0本机并行交叉编译，不使用 xgo。等价于 make release-native
task release:verify VERSION=1.2.0 DIST=dist/1.2.0重新校验完整制品矩阵、tar.gz 包内字节与 SHA256SUMS 回读

运行单个测试

Go 测试

# 运行单个测试函数
go test -run '^TestFunctionName$' ./modulepath/...

# 带竞态检测
go test -race -run '^TestFunctionName$' ./modulepath/...

JavaScript/TypeScript 测试

# 运行单个测试文件
pnpm exec vitest path/to/test.spec.ts

# 运行 E2E 测试
GITEA_TEST_E2E_FLAGS='path/to/test.spec.ts' task test:e2e

代码规范

Go

  • 使用 gofmt 格式化
  • 通过 golangci-lint 静态检查
  • 新文件在版权头添加当前年份
  • 无尾随空白

TypeScript

  • 使用 !（非空断言）代替 ?./??（当值确定存在时）
  • 通过 eslint 检查

CSS

  • 优先使用 flex-* 布局辅助类
  • 仅在需要 !important 特异性时使用 tw-* 工具类

Git 提交

  • 使用 Conventional Commits：type(scope): subject
  • Breaking change 在冒号前加 !
  • 测试变更使用 test 类型
  • 提交信息末尾添加 Assisted-by: AGENT_NAME:MODEL_VERSION
  • 不要 force-push、amend 或 squash

发布流程

重要

项目不使用 GitHub Actions。所有格式化、静态检查、测试、竞态检查、镜像验证、跨平台打包和发布验证均在本地完成。

  1. 本地运行 task fmt、task lint:go、task lint:js、task test
  2. 交叉编译并打包 Linux、macOS、Windows 目标
  3. 验证 checksum 和签名
  4. 使用 gh 创建 tag 和发布

不发布增量版本。完成全部需求验证后，创建一个统一的 tag 和发布包。

文档维护

功能、配置、安装、升级、卸载、API、安全、架构或工作流发生变化时，同一变更必须同步更新相关 Markdown 与 docs/site/ HTML 页面。新增页面必须加入 文档首页和侧边导航。

面向自动化协作者的规则、验证步骤或仓库约束变化时，还必须更新 git-next 客户端 Agent 协作页面与根目录 AGENTS.md。

治理与安全

贡献流程见仓库根目录 CONTRIBUTING.md，安全漏洞按 SECURITY.md 的私密渠道报告，行为准则见 CODE_OF_CONDUCT.md。这些文件描述 Gitsss 当前治理，不使用上游项目的联系人或维护者名单。

同分支 push 接收链路

目标是同一仓库同一分支每秒至少 100 次独立成功的 Git 事务，拒绝、重试和一次 push 中的多个提交不计入成功次数。v1.16.0 最终 Linux amd64 CGO 包在 WAL/NORMAL 配置下，以 16 个连续在途请求完成 512 次独立成功更新，零重试，119.76 次/秒。包含本机 Git/LFS/PR、权限、hooks、数据库与重启完整性的整批验收耗时 50.907 秒。Windows CLI 与 FULL 同步的结果分别记录。

Trace2 显示主要开销在每次 hook 启动完整应用。已提供随服务端构建的轻量 gitsss-hook，通过原内部 API 继续执行权限与分支处理；只有匹配受信模板且未设置自定义 hooksPath 的仓库才采用逐次命令覆盖，自定义 hook 保留原顺序、输入、参数和退出结果。

兼容性：不重写 bare 仓库、原 hooks、对象、refs、LFS 或数据库 schema；代理脚本仅位于 layout v1 的 gitsss/extensions/receive-hooks/。回退服务端即可恢复原链路，fsync 与原生 refs 事务不变。已在本机完成主程序与辅助程序的七平台交叉编译，性能结论限定为上述 Linux CGO 配置。

同分支依赖仅在内存中登记：完成前置校验后最多等待已知在途前驱 250 ms，提交、失败或取消均唤醒；随后仍由 Git 原子比较旧 OID。其他 refs 不等待，不形成全仓库互斥或新的持久化存储。未知、签名或过大协议头保留原字节交给 Git。

并发基准默认维持固定在途请求数，逐次补入新的独立事务；pack 的滑动祖先窗口最多为 worker 数。报告列出调度方式、上传字节、成功更新和竞争拒绝。协议吞吐测量完成后，CLI 与 Git/LFS/PR 两组功能验证并行执行。

后置回调回写分支元数据前核对当前 Git ref，并以数据库原 commit_id 作条件更新，避免旧回调覆盖新快照。单分支不在读取 Git 时持有 SQLite 读事务；活动和通知继续按原队列处理。模型初始化回调注册条件已修复，令牌缓存命中后仍逐次检查数据库中的撤销和 scope；认证只更新最近使用时间，同一秒内避免重复写入。

主程序同目录安装匹配版本的 gitsss-hook（Windows 为 gitsss-hook.exe）。Docker 镜像与 backend 构建包含辅助程序，原生发布同时生成主程序、辅助程序和校验值。Unix 内置 hook 可直接执行；自定义 hook 使用原分发器并恢复嵌套 Git 的 hooksPath。SQLITE_SYNCHRONOUS 留空保留原驱动默认，可显式设置一致级别；日志模式不自动修改，NORMAL 与 FULL 的性能分别记录。诊断原始数据只保存在本机。

详细迁移、容量、回滚和验收范围见仓库 docs/features/push-throughput.md；协议依据为 Git hooks，对照架构为 Cursor Git at any scale。

原生发布在缺少 xz 时使用 Python 3 的 lzma（可用 PYTHON 指定解释器）；发布前逐个解压回读，与原始产物 SHA-256 比对。

每个平台的 tar.gz 组合包同时包含主程序、gitsss-hook、许可证和安装说明，自动更新选择唯一组合包。原始文件与 XZ 保留兼容；CGO 变体使用明确附件名选择。build/package-native.py 可独立重打包。
